# 发布前检查（xinghe-helper）

上线前、提交前、验收前，把这个技能跑一遍。**任何一项 FAIL 都不要发布**，先修再跑。

## 一、怎么用

```bash
node .workbuddy/skills/verify-project/verify.mjs
```

- 在**项目根目录**运行（脚本靠 `package.json` 定位自己，找不到会报错）。
- 退出码：`0` = 全部通过；`1` = 有FAIL。
- 输出格式：`PASS / FAIL / SKIP+ 一行证据`。证据里带具体文件行号，能直接点开核对。
- 不需要联网、不需要部署，纯静态检查，随时能跑。

## 二、九个检查项与来源

每项都对应本项目**真实踩过的坑**，不是凭空设想。

### 1. 密钥未进仓库（含 Git 全历史）

- **为什么查**：密钥可能提交过、后来删掉。`git log -p` 能看到所有历史 diff——**代码删干净≠密钥没泄漏过**。
- **命令**：`git log --all -p --full-history | grep -nIE "$SECRET_RE"`
- **通过**：0 条命中。
- **坑来源**：Day 23·安全自查1.2。

### 2. `.env` 未入库、`.env.example` 已入库

- **为什么查**：`.env` 是真值永远不能进；`.env.example` 是模板必须进（别人要知道配哪些变量）。
- **命令**：`git log --all --diff-filter=A --name-only --format="" | sort -u | grep -iE '(^|/)\.env'`
- **通过**：只出现 `.env.example`；同时 `git check-ignore -v web/.env` 要命中 `.gitignore`。
- **坑来源**：Day 23 · 安全自查 1.3 / 4.2。

### 3. CORS 白名单含托管域名

- **为什么查**：CloudBase 虽会自动加托管域名，但**代码里必须显式写上**——平台升级或换环境时自动行为不一定还有效。实测正式域名返回 418，真正生效的是带数字后缀那个，两个都得在。
- **命令**：检查三个 `cors.js` 的 `DEFAULT_ORIGINS` 是否含 `tcloudbaseapp.com`。
- **通过**：三个函数目录的白名单都含托管域名。
- **坑来源**：Day 20 · 卡点 2/3。

### 4. CORS 三处副本同步⚠️

- **为什么查**：CloudBase 只打包函数自己的目录，所以三个函数各有一份 `cors.js` 副本。**改一处不改另外两处 = 只有一个接口能用**，这是 Day 20 卡了两次才定位的问题。
- **命令**：把三份 `DEFAULT_ORIGINS` 提取出来比对，必须完全一致。
- **通过**：三份内容逐字相同。
- **坑来源**：Day 20 · 「改白名单时三处都要同步」。

### 5. 密钥走环境变量、无数据库连接串

- **为什么查**：硬编码密钥 = 泄漏。连接串里带密码。
- **命令**：查 `process.env` 的读取位置；查有没有 `DB_URL` / `PGPASSWORD` / `app.rdb` 混用。
- **通过**：只读 `PG_SCHEMA` / `ALLOWED_ORIGINS`；数据库只走 `app.rdb()` 平台网关，无任何连接串和密码。
- **坑来源**：Day 20 / Day 23 · 安全自查 1.5 / 1.6。

### 6. 服务端无裸报错

- **为什么查**：把 `error.message`拼进响应，等于把表名、SQL 片段、字段名送给任何人——拿到接口链接的人随便调一次就能看到，不需要绕过任何权限。
- **命令**：`grep -rn "fail(500\|\.message ||" cloudfunctions/*/index.js`
- **通过**：0 处（Day 23 已把 31 处改成 `failServer()`）。
- **坑来源**：Day 23 · 修复主体。

### 7. 写操作按钮防连点（两件套）⚠️

- **为什么查**：Day 24 的真实 bug——快速连点发出 5 个 POST。而且 `disabled` **只挡鼠标**，表单里按回车走 `onSubmit` 会完全绕过它，所以必须两件套。
- **命令**：找所有写操作按钮，检查有没有 `disabled={!!busy}`；对应函数开头有没有 `if (busy) return`。
- **通过**：每个写操作两个防线都在。
- **坑来源**：Day 24 · Bug 修复记录。
- **注意**：按钮的 `disabled` 和函数的 `if (busy) return` **缺一不可**，只写一个等于没修。

### 8. 仓库换行符为 LF

- **为什么查**：用脚本 `open(f,'w')` 改文件会写成 CRLF，导致 git diff 每行都算改动——Day 23 一度膨胀到 1883 行，污染 git 历史。
- **命令**：扫描已跟踪文件里有无 `\r\n`。
- **通过**：0 个文件含 CRLF。
- **坑来源**：Day 23 · 换行符污染。

### 9. 带 id 的接口用查询参数

- **为什么查**：控制台 Path passthrough = Disable，`/:id` **传不进云函数**。写成路径参数会 404 或拿不到 id。
- **命令**：检查有无 `/api/xxx/:id` 形式的路径路由。
- **通过**：带 id 的接口一律 `?id=&camp_id=` 查询参数。
- **坑来源**：契约约定 · 路由形态。

## 三、判定纪律

1. **不允许「大概没问题」**。每项要么 PASS 要么 FAIL，附文件行号。
2. **检查项自身也可能错**。跑出意料结果时，先怀疑检查项写错了，再怀疑项目错了——这就是要跑两轮的意义。
3. **改完必须重跑**，确认从 FAIL 变 PASS。
4. **检查项不能自己骗自己**：故意弄坏一项，它必须报 FAIL；修好后必须报 PASS。**一个永远报 PASS 的检查项等于没有检查项。**

## 四、故意弄坏验证（发布前必做）

新加或修改检查项后，必须做一次反向验证：

1. 挑一项**静态可查、改动可完全还原**的检查项（推荐第 4 项 CORS 同步）。
2. 手动弄坏它（模拟「只改了一处就部署」的真实场景）。
3. 跑技能 →该项**必须**报 FAIL。
4. `git checkout --<文件>` 还原 → 重跑 → 必须回到 PASS。

只有走完这四步，才算证明这个检查项真的在检查东西。
