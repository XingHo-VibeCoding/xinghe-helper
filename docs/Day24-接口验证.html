第 3 步是整个定位过程里最值钱的一步：并发实测决定了这是「体验 Bug」还是「数据损坏 Bug」。 如果没做这一步，很可能会跑去「加固后端」—— 但后端本来就是对的。

定位捷径：找 Bug 时，问「这个按钮应该怎么写」不如问「同一个文件里其他按钮怎么写的」。 AI 分房按钮（第 397 行）、重新分房（401）、恢复 AI 方案（404）都写了 disabled={!!busy}， 唯独添加房间漏了。→ 漏的不是不会写，是少写一处。照着邻居写比自己想设计更可靠。
还有一点：busy 状态本来就是现成的。 handleAddRoom 里早就有 setBusy('保存中…') 和 setBusy('')， 只是没人拿它来禁用按钮。状态有了、逻辑有了，只差一个绑定。

为什么两处都要改（不是多此一举）
防线拦什么为什么按钮的 disabled 不够
disabled={!!busy}鼠标点击 在 <form> 里按回车键会直接触发 onSubmit， 这条路径完全不经过按钮，disabled 拦不住。 用户把光标放在房号输入框里连按回车，同样会重复提交。
if (busy) return回车提交 / 程序化调用
为什么不用现成的 AsyncButton 组件：它需要页面维护一个独立状态（status）， 而 busy 已经是这个角色了；而且本文件第 397/401/404 行用的就是 disabled={!!busy} 这种写法， 同一个文件里两种写法会让后来的人困惑。选改动最小、和现有代码一致的那个。
