# 第二部分：结营演示提纲（3–5 分钟）

## 【用户问题】（30 秒）

> 「口语营结束前三天，我要在两小时内把 40 多个学生排进房间。男女生不能混住，打呼的和睡眠差的不宜同房，有人想和室友合住但不能超过 6 人——我一个人用 Excel 排，改一个就要重排一遍，还总怕漏掉谁。」

**真实痛点**：住宿安排是**反复重排**的活，不是排一次就完的。Excel 排错了没法追责，也没法撤销。

**这个项目的定位**：它是 28 天里交付的 v1.0 作品。打卡应用只是示范案例——**真正的作品是「把一件反复出错的手工活，变成一个可撤销、可追溯、不会漏人的工具」**。

## 【核心流程】（1.5 分钟）

**Step 1｜学生填表（20 秒）**

打开 `/form` 页面截图。字段：姓名、性别、带班老师、年级班级、入住日期、期望拼房人数、是否打鼾、睡眠质量、备注。

> 话术：「学生扫二维码自己填，**零注册**。填完立刻入库，组织者工作台马上能看到——不需要我手动录任何一个人。」

**Step 2｜AI 一键分房（30 秒）**

在 `/workbench` 点「一键 AI 分房」，展示绿条反馈「AI 分房完成：N 人已全部入房」，页面房间卡片实时更新。

> 话术：「三条红线由代码保证：**男女混住拒绝、超员拒绝、睡眠冲突允许但黄标提醒**。为什么睡眠冲突只提醒不拒绝？因为偶尔有特殊情况，人比规则灵活。」

**Step 3｜手动微调（20 秒）**

把未分配学生拖进房间。展示拖拽时的**红线即时反馈**——拖向不合法房间时虚线框变红。

> 话术：「AI 是给建议，不是替我做决定。最后的安排永远由人能改。」

**Step 4｜删掉填错的人（20 秒）** ← 今天新加的

点未分配学生卡片右侧「删除」，弹二次确认：「他填的入住日期、带班老师、想拼几人都会一起消失，而且找不回来。」

> 话术：「今天新增的功能。之前学生填错了**删不掉**——因为项目最初的设计是'保留痕迹'。我给出两个方案让你选：标记失效（可恢复）vs 物理删除（不可恢复）。你选了物理删除，我按这个做了，并把外键依赖问题一起解决了。」

**Step 5｜刷新验证（10 秒）**

刷新页面，数据全部还在，顶部「最后更新 12:46:51」时间戳变化。

> 话术：「**数据在云端，不在浏览器里**。换台电脑登录，名单一样在。」

## 【验证方式】（1 分钟）

**核心原则：不相信接口自己说成功，要去数据库看。**

三层验证（今天全部实测）：

```
① 接口层：curl 真实调用线上接口
② 数据库层：tcb db execute 直接查表核实
③ 产物层：curl 拉线上 JS，比对哈希，确认部署真生效
```

**举例 —— 部署验证踩过的坑**：

> 「Day 23 我遇到过一个情况：控制台显示『部署成功』，Modification time 也更新了，**但云端代码其实没推上去**——函数名搜不到新的。表面成功、实际没生效，比直接失败还危险。」

所以我形成了一条规矩：**部署后必须 `tcb fn detail` 查 Code size + 拉线上 bundle 搜中文文案**，两样都对才算成功。今天三次部署全部按这个验证。

**今天的一个反面教训**（我自己犯的错，主动说）：

> 「今天测『已入房不许删』时，我写了 `PATCH 分房` + `DELETE` 两步，但没检查第一步是否真的成功。PATCH 因为房间不存在失败了，学生没入房，拦截没生效，DELETE 把他真删了。」
>
> **教训：验证『前提是否成立』时，必须查数据库的真实状态，不能只看自己发的请求。** 后来重做，每一步都用 `tcb db execute` 核实后再继续。

**不粉饰，说清三条真实的墙**：

| 限制 | 影响 | 我的处理 |
|---|---|---|
| **体验版 2027-04-03 到期，且不能自助续费** | 到期后没有自己能走通的补救路径 | 记日历，设 2027-02-02 提醒，提前 90 天决定升级 |
| **无登录态，接口链接 = 操作权限** | 拿到链接的人能提交/删除报名数据 | 收紧 CORS 白名单（外部网站发不出跨域请求）+ 路径隐藏。但**这挡不住 curl**——接入真实学生数据前必须先加登录态校验 |
| **控制台路径 passthrough = Disable** | `/:id` 传不进云函数 | 所有带 id 的接口改用查询参数 `?id=&camp_id=` |

**还有一条我要特别说**：

> 「项目里有 13 个接口挤在 2 个云函数里，不是乱写。控制台只能配 3 条 HTTP 路径映射（`/api/health`、`/api/rooms`、`/api/students`），想加新路径得去控制台改配置。与其赌平台行为，不如在一个函数内按 `httpMethod + action` 自己分流。」

## 【后续优化计划】（30 秒）

**按优先级，说清为什么这么排**：

**P0｜上线前必做**
- 加登录态校验，收回 anon 写权限（尤其 DELETE）
- 当前 DELETE 权限下，链接泄露 = 名单可被删

**P1｜真实使用会遇到的**
- 批量删除：现在要一个个点。40 人的营若有 10 个填错，操作成本太高
- 数据导出 CSV：给主办方一份纸质名单
- 防连点统一封装：现在每个按钮都要手写 `disabled + if(busy) return`，容易漏（Day 24/26 各漏过一次）

**P2｜架构改进**
- `students` 表加 `deleted_at` 软删除字段，用一个字段同时满足「真删」和「可追溯」—— 今天的物理删除丢掉了痕迹，如果当初是这个设计就不用做两难选择
- 一键分房现在在服务端循环逐条 update，**不是真事务**，中途失败会留半套数据。几十人规模可接受，上百人需要存储过程

**P3｜技术债**
- `assignment_history` 快照存整份 JSON，数据量大了会膨胀，考虑只存增量
