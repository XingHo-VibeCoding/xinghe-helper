第 3、4 条是「不碰数据库就能拦住的」。 它们发生在参数校验阶段——比等到数据库报英文的 check violation 再翻译回来更早、更快、提示也更准。 第 4 条对应的数据库约束是 check (capacity > 0)（见 db/schema.sql）： 校验层和数据库约束是两层防护，两层都要有。

④ 前端删除的二次确认Day 20 已实现

今天要掌握的问题—— 你在哪加了确认？为什么加在这里？
// web/src/pages/Workbench.jsx · handleDeleteRoom(room)
const members = roomMembers(students, room.id)
const ok = window.confirm(
  `确定删除 ${room.room_no} 房?` +
    (members.length ? `里面的 ${members.length} 人会回到未分配名单。` : ''),
)
if (!ok) return   // 用户点了取消，到此为止，一个请求都不发
const res = await deleteRoom(room.id)
确认里写了什么为什么要写这句
房号（`确定删除 301 房?`） 让用户确认删的是哪一间。房号是给人看的身份，比 id=101 直观得多
连带影响的人数（里面的 3 人会回到未分配名单） 这是关键。删除的代价不是「少一间房」，而是 3 个人的住宿安排被清空。 不说的话，用户只会以为是删个空房间
人数为 0 时不显示这句 避免出现「里面的 0 人会回到未分配名单」这种让人以为还有人要处理的废话
为什么确认必须放在前端，不能只靠后端： 后端能保证「删房 + 放人」是原子的（要么都成功要么都不做）， 但它没法阻止用户点错。二次确认是最后一道闸门， 而且它能提供后端给不了的东西——把连带影响提前说出来，让用户在数据还没变时就做决定。

增删改查四类操作闭环✓ 通过 POST 建 → PATCH 改 → GET 查 → DELETE 删，串成一条链走完，每步都留接口 + 数据库两处证据
闭环的价值在于「每一步都验证了上一步的结果」。 单测四个接口各自返回 ok:true 不叫闭环—— 那只能证明「每个按钮按下去没报错」。 闭环要证明的是：改完再查，查到的是新值；删完再查，查不到了。
