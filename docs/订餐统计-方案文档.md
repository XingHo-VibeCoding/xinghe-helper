# 订餐统计功能 —— 方案文档

> 状态：**方案已设计，未动工**（等数据库从 Isolated 恢复后才开始实施）
> 日期：2026-10-17
> 定位：**xinghe-helper 的新功能模块**，不是独立项目

---

## 0. 一句话概括

**组织者每天生成两张带日期的二维码（学生一张、工作人员一张）→ 两批人分别扫码填表 → 组织者得到一张按班级/部门分组的订餐人数汇总表，学生与工作人员**完全分开**。**

---

## 1. 为什么这个功能很轻

### 1.1 复用了什么（不用重做）

`students` 表里**已经有** `teacher` 和 `class_level` 两个字段，且都是必填：

```
teacher      varchar(20)  →  Mona / Kiven / Selena / Betty / Priya
class_level  varchar(10)  →  星一 / 星二 / 星三
```

而用户的组织结构恰好是：

> 「Mona 老师，就会有Mona 星一、Mona 星二、Mona 星三之分」

**所以「班」= 老师 + 年级的组合，5 个老师 × 3 个年级 = 15 个班。**
这个组合已经隐含在现有数据里，不需要新建班级表，不需要加字段。

### 1.2 不动什么

| 对象 | 改动 |
|---|---|
| `students` 表结构 | **不改** |
| `camps` / `rooms` / `assignment_history` | **不改** |
| 住宿学生填表页 `/form` | **不改**（订餐是独立页面） |
| 分房工作台 / 名单总览 | **不改** |

### 1.3 新增什么

| 类型 | 数量 | 说明 |
|---|---|---|
| 数据表 | 1 张 `meal_orders` | 存订餐记录（学生 + 工作人员同一张表） |
| 接口 | 3 个 | 提交订单 / 查汇总 / 查有订餐的日期 |
| 页面 | 4 个 | 二维码生成 / 学生填 / 工作人员填 / 汇总表 |

## 2. 两批人分别填什么

### 2.1 学生：五道题

| # | 题目 | 类型 | 必填 |
|---|---|---|---|
| 1 | 你的名字是？ | 文本 | ✅ |
| 2 | 你是哪位老师带的？ | 单选（5 个老师） | ✅ |
| 3 | 你在哪个班？ | 单选（星一/星二/星三） | ✅ |
| 4 | 今天中午订吗？ | 单选（订 / 不订） | ✅ |
| 5 | 今天晚上订吗？ | 单选（订 / 不订） | ✅ |

**分组逻辑**：老师 + 年级 → 15 个班。

### 2.2 工作人员：三道题

| # | 题目 | 类型 | 必填 |
|---|---|---|---|
| 1 | 你的名字是？ | 文本 | ✅ |
| 2 | 你在哪个部门？ | 单选（教学部 / 市场部 / 其他部门） | ✅ |
| 3 | 今天中午订吗？ | 单选（订 / 不订） | ✅ |
| 4 | 今天晚上订吗？ | 单选（订 / 不订） | ✅ |

**分组逻辑**：部门 → 3 个部门。

⚠️ **明确不做的**（用户拍板）：
- **不问「你是老师还是创客」** —— 只按部门分，不细分身份
- **不填老师/年级** —— 工作人员不分班

### 2.3 两批人字段差异对照

| 字段 | 学生 | 工作人员 | 说明 |
|---|---|---|---|
| 姓名 | ✅ | ✅ | 两边都要 |
| 老师 / 年级 | ✅✅ | ❌ | 只有学生分班 |
| 部门 | ❌ | ✅ | 只有工作人员填 |
| 午饭 / 晚饭 | ✅✅ | ✅✅ | 两边一致 |
| 身份 role | `'student'` | `'staff'` | **由页面写死，不让用户填** |

⚠️ **`role` 由页面写死是关键安全设计**：如果让用户在表单里选「我是学生还是工作人员」，
就等于把区分责任交给填表的人 —— 一旦手滑选错，数据就错了。
由两个不同的页面各自写死，前端根本没有出错的余地。

## 3. 两张二维码怎么区分（用户强调「一定不能搞混」）

### 3.1 核心原则

**不能只靠链接不同区分。** 扫码的人不会去读地址栏那行小字，
两个二维码图案长得几乎一样（只差几个像素），肉眼根本分不出。

**必须三层同时生效，任何一层失效还有下一层兜住。**

### 3.2 三重区分

| 层 | 手段 | 为什么这一层有用 |
|---|---|---|
| **第1 层** | **图片带标题和颜色** —— 学生版蓝色顶部写「学生订餐 · 1月20日」，工作人员版橙色写「老师与创客 · 1月20日」 | 打印出来往桌上一放，**扫之前就能看见差别**。这是唯一能在扫码前起作用的层 |
| **第 2 层** | **链接路径不同** —— `/meal?date=X` vs `/staff-meal?date=X` | 两条完全独立的路由，不共用入口。技术上不可能走错 |
| **第 3 层** | **页面第一屏点明身份** —— 学生页写「如果你是老师或创客，请换一个码」，工作人员页反之 | 即使前两层都失效（贴错纸、扫错码），**打开页面立刻发现自己填错了**，不会闷头填完 |

### 3.3 二维码图片的具体做法

在现有 `FormQrCode.jsx` 的下载逻辑基础上，把二维码画到一张**带标题的卡片**上：

```
┌─────────────────────┐
│  学生订餐 · 1月20日    │  ← 蓝色标题栏
│                     │
│    ▓▓▓▓▓▓▓▓▓         │
│    ▓▓   ▓▓▓▓▓       │  ← qrcode.react画出来的码
│    ▓▓▓▓▓▓▓▓▓         │
│                     │
└─────────────────────┘
```

实现方式：新建一个 `<canvas>`，先填色画标题栏文字，再把 `QRCodeCanvas`
的内容 `drawImage` 到下方，最后 `toDataURL('image/png')` 下载。
（现有代码是直接从 `.qr-box canvas` 取，改造后要改这个选择器。）

⚠️ **两个文件的下载文件名也必须不同**：
- `学生订餐-2027-01-20.png`
- `老师与创客订餐-2027-01-20.png`

## 4. 数据库设计

### 4.1 新表 `meal_orders`

```sql
-- ============================================================
-- meal_orders —— 每日订餐记录（学生 + 工作人员同一张表）
-- ============================================================
-- 一条记录 = 某人在某一天的订餐选择
--
-- 【为什么不建外键到students】
--   订餐和住宿是两件独立的事。工作人员根本不订房，
--   建外键会让「工作人员订餐」插不进来。学生也可能只订餐不订房。
--
-- 【为什么用一张表而不是两张】
--   两张表意味着两套接口、两套前端表单、两套汇总逻辑，
--   但两边字段有 4 个是重合的（姓名 / 午饭 / 晚饭 / 日期）。
--   一张表 + 一个 role 字段更简单，汇总时按 role 分组即可。
-- ============================================================
create table public.meal_orders (
  id          bigserial   primary key,
  camp_id     bigint      not null references public.camps(id),

  -- 哪一天的餐。这个值来自二维码链接里的 ?date=
  meal_date   date        not null,

  -- 身份：学生还是工作人员。
  -- ⚠️ 由页面写死，不让用户填（见 2.3 节的理由）
  role        varchar(10) not null,

  name        varchar(50) not null,

  -- 下面两个字段只有 role='student' 时有值，role='staff' 时为 NULL
  teacher     varchar(20),
  class_level varchar(10),

  -- 下面这个字段只有 role='staff' 时有值，role='student' 时为 NULL
  department  varchar(20),

  lunch       boolean     not null,
  dinner      boolean     not null,

  created_at  timestamptz not null default now(),

  constraint meal_role_valid     check (role in ('student', 'staff')),

  -- 取值约束跟 students 表保持一致（同一批选项），
  --   避免两处口径不一致导致某个班凭空消失
  constraint meal_teacher_valid  check (teacher is null or teacher in ('Mona', 'Kiven', 'Selena', 'Betty', 'Priya')),
  constraint meal_class_valid    check (class_level is null or class_level in ('星一', '星二', '星三')),
  constraint meal_dept_valid     check (department is null or department in ('教学部', '市场部', '其他部门')),

  -- 【交叉约束】身份和字段必须自洽：
  --   学生 → 必须有老师+年级、且没有部门
  --   工作人员 → 必须有部门、且没有老师+年级
  --   这一条是防「学生填了部门」这类脏数据的最后一道闸。
  --   为什么需要：不加的话，脏数据会静默进入汇总表，
  --   表现为某个班人数莫名多1 或者部门人数多 1，极难排查。
  constraint meal_role_fields_consistent check (
    (role = 'student' and teacher is not null and class_level is not null and department is null)
    or
    (role = 'staff' and department is not null and teacher is null and class_level is null)
  )
);

-- 判重：同一身份 + 同一天 + 同一分组 + 同一姓名 只能有一条
--
-- ⚠️ 这里用 COALESCE 把 NULL 当成空串处理，
--   否则 staff 记录（teacher 为 NULL）在 PG 里
--   unique 索引认为 NULL ≠ NULL，
--   同一个工作人员能插出无数条重复记录。
--
-- 例：'student' + '2027-01-20' + 'Mona' + '星一' + '林小满' 只能一条
--     'staff'    + '2027-01-20' + ''    + ''    + '张伟'   只能一条
create unique index idx_meals_uniq_per_day
  on public.meal_orders (
    camp_id, meal_date, role,
    coalesce(teacher, ''), coalesce(class_level, ''), coalesce(department, ''),
    name
  );

-- 按天查全部订单（汇总页主查询）
create index idx_meals_by_date on public.meal_orders (camp_id, meal_date);
```

### 4.2 判重逻辑

**学生：姓名 + 老师 + 年级 · 工作人员：姓名 + 部门**（均含 role 与日期）

行为：同一人同一天重复提交 → **覆盖**旧记录（不报错），页面提示「已更新你的订餐」。
与住宿页行为一致。

⚠️ **已知取舍**（用户拍板）：
- 不收手机号。学生用「姓名+老师+年级」，工作人员用「姓名+部门」。
- 风险：同名同组的极小概率撞车，后提交者覆盖前一个，数字少 1 份。
- 住宿表那边是按手机号判的（Day 28 的教训），订餐表不用——为了不增加填表负担。

**实现方式**：`insert ... on conflict (...) do update set lunch = excluded.lunch, dinner = excluded.dinner`
—— 一次 SQL 搞定，不存在「先查后插」的竞态。
⚠️ `on conflict` 的目标必须是上面那个**表达式唯一索引**，写法要注意。

## 5. 接口设计

统一走 `{ ok, data, error }` 信封（与现有 13 个接口一致）。
⚠️ 带 id / date 的参数一律用**查询参数**，不能用路径参数（Path passthrough = Disable）。

### 5.1 提交订餐

```
POST /api/meals
Content-Type: application/json

{
  "camp_id": 1,
  "meal_date": "2027-01-20",
  "role": "student",              ← 由页面写死
  "name": "林小满",
  "teacher": "Mona",
  "class_level": "星一",
  "lunch": true,
  "dinner": false
}
```

工作人员版：

```json
{
  "camp_id": 1,
  "meal_date": "2027-01-20",
  "role": "staff",
  "name": "张伟",
  "department": "教学部",
  "lunch": true,
  "dinner": true
}
```

响应：

```json
{ "ok": true, "data": { "id": 42, "updated": false }, "error": null }
```

- `updated: true` = 重复提交，已覆盖 → 前端显示「已更新你的订餐」
- `400 INVALID_MEAL_DATE` = 日期格式不对
- `400 ROLE_FIELDS_MISMATCH` = role 与字段不自洽（如 role=student 却传了 department）

⚠️ **服务端必须自己按 role 校验字段组合**，不能只靠数据库 CHECK：
   报错信息要说人话（「学生订餐不用填部门」），而不是抛数据库约束名。

### 5.2 查订餐汇总

```
GET /api/meals?action=summary&camp_id=1&meal_date=2027-01-20
```

响应：

```json
{
  "ok": true,
  "data": {
    "meal_date": "2027-01-20",
    "student": {
      "total": { "lunch": 128, "dinner": 126, "people": 130 },
      "classes": [
        { "teacher": "Mona", "class_level": "星一", "lunch": 15, "dinner": 12 }
      ]
    },
    "staff": {
      "total": { "lunch": 8, "dinner": 8, "people": 9 },
      "departments": [
        { "department": "教学部", "lunch": 5, "dinner": 5 },
        { "department": "市场部", "lunch": 2, "dinner": 2 },
        { "department": "其他部门", "lunch": 1, "dinner": 1 }
      ]
    },
    "grand": { "lunch": 136, "dinner": 134 }
  },
  "error": null
}
```

**统计口径**：
- 学生 **15 个班全部返回**，没人的显示 0（否则分不清「没人订」和「班不存在」）
- 工作人员 **3 个部门全部返回**，没人的显示 0
- ⚠️ **学生的数据绝不能混进 `staff`**，`role='staff'` 的查询条件写死在 SQL 里
- 没有订单的日期返回计数 0 + 空数组，**不报错**

### 5.3 查有订餐记录的日期（给汇总页做日期切换）

```
GET /api/meals?action=dates&camp_id=1
```

响应：`{ "ok": true, "data": { "dates": ["2027-01-20", "2027-01-21"] }, "error": null }`

## 6. 页面设计

### 6.1 `/meals/qr` —— 组织者生成当天二维码

- 日期选择器（默认今天）
- **两个并排的生成按钮**：蓝色「生成学生码」/ 橙色「生成老师与创客码」
- 点击后各自展开对应的带标题二维码卡片
- 「下载 PNG」按钮，文件名带身份前缀（见 3.3 节）
- 提示语说清：**「今天的码只对 X 月 X 日有效」**
- ⚠️ 两个按钮的 `busy` 状态**必须分开**，不能共用一个 —— 否则点一个另一个也置灰

⚠️ 防连点两件套：`disabled={!!busy}` + 函数入口 `if (busy) return`

### 6.2 `/meal` —— 学生填表页（**公开页，不显示导航**）

- 日期从 URL `?date=` 取，**不显示日期选择器**（防止填错日期）
- 顶部醒目提示：**「学生订餐登记」**
- ⚠️ **身份反提示**：页面底部固定一条「如果你是老师或创客，请换一个二维码」
- 五道题，「订/不订」用不同颜色（订=绿，不订=灰）
- 提交后确认页：「今天的订餐已收到」+ 重填按钮
- URL 缺 `date` → 「这个二维码不对，请找组织者拿今天的码」

### 6.3 `/staff-meal` —— 工作人员填表页（**公开页，不显示导航**）

- 顶部醒目提示：**「老师与创客订餐」**
- ⚠️ **身份反提示**：「如果你是学生，请换一个二维码」
- 三道题（姓名 / 部门 / 午饭 / 晚饭）
- 其余交互与学生页一致

⚠️ **两个页面都不要加进 `App.jsx` 的 `ORGANIZER_PATHS`**，导航对填表者完全隐藏。

### 6.4 `/meals/summary` —— 汇总表（打印友好）

- 顶部：日期切换（下拉，从 `action=dates` 拿）+ 「打印」按钮
- **主体分两大块，中间明显分隔**：

```
1 月 20 日 订餐汇总
──────────────────────────────────────
【学生】                      午餐 128  晚餐 126
Mona 星一15    12
  Mona 星二                        11    11
  ...
──────────────────────────────────────
【老师与创客】午餐8    晚餐    8
  教学部                              5     5
  市场部                              2     2
  其他部门                            1     1
──────────────────────────────────────
合计                                  136   134
```

- 打印样式：黑白、加粗合计行、两大块之间加分隔线
- 空状态（这天没人填）：提示「今天还没有人提交订餐」+ 显示二维码入口

## 8. 待确认 / 风险

### 8.1 必须先解决的

- **数据库 Isolated**：不恢复则第 1 步就做不了
- **接口路由被 api-mona 挤掉**：新增接口必须挂在合并后的函数上

### 8.2 已知的取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| 不收手机号 | 学生三项判重 / 工作人员两项判重 | 用户不想加题；风险是极小概率同组同名撞车 |
| 不收忌口 | 只统计人数 | 用户明确选了「只算人数」 |
| 不做明细名单 | 只要汇总表 | 用户明确选了「一张人数汇总表」 |
| 每天两张新码 | 链接带 `?date=` | 防止学生填错日期 |
| 不问老师还是创客 | 只按部门分 | 用户明确选择 |
| 一张表存两批人 | `role` 字段区分 | 字段重合 4 个，两张表要维护两套逻辑 |
| 不碰餐厅对接 | 永久不做 | 与 PRD「永远不碰酒店对接和支付」一致 |
