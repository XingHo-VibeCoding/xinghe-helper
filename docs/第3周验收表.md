**验证方法**：对每个接口发真实 HTTP 请求，记录状态码与响应体；写入类接口做「写前计数 → 写入 → 重查确认 → 删除还原」闭环。

**逐条实测记录**

| 接口 | 方法 | 验证动作 | 实测结果 |
|------|------|---------|---------|
| `/api/health` | GET | 直连 | HTTP **200** `{"ok":true,"service":"xinghe-helper"}` |
| `/api/rooms?camp_id=1` | GET | 直连 | HTTP **200**，返回 13 条房间 |
| `/api/students?camp_id=1` | GET | 直连 | HTTP **200**，返回 14 名学生 |
| `/api/rooms` | POST | 真实写入 | HTTP **200** `{"ok":true,"data":{"id":119}}` |
| `/api/rooms?id=119&camp_id=1` | DELETE | 删除还原 | HTTP **200** `{"id":119,"unassigned_count":0}` |

**写入闭环四步证据**（这是本周最硬的一条）
```
1. 写入前GET /api/rooms  →  13 条
2. POST {"room_no":"399","capacity":4,"gender_label":"女"}
                →  {"ok":true,"data":{"id":119}}
3. 另起新连接重新 GET→  14 条，且查到
                {"id":119,"room_no":"399","capacity":4,
                 "gender_label":"女",
                 "created_at":"2026-10-08T11:14:30+08:00"}
4. DELETE /api/rooms?id=119&camp_id=1
                →  回到 13 条，399 已消失
```

**关键点**：第 3 步是**另一次独立请求**读出来的，不是拿 POST 的返回结果自证。所以「数据真的落库了、且刷新后还在」这件事是被证过的，不是推测的。

**顺带发现（非FAIL，但演示时要知道）**：`DELETE /api/rooms/119?camp_id=1`（路径带 id）返回 400，因为契约规定 id 走 **query 参数**而非路径。这与 `api-contract.md` 第 2.8 节写法一致，属调用方需按契约传参，不是后端缺陷。同理 `camp_id` 缺失时会返回 `400 VALIDATION_ERROR`，属于设计好的参数校验。
