## 五、最高优先级问题

| 项 | 内容 |
|---|---|
| **问题一句话描述** | 表单校验显示全绿但提交必失败：前端校验查驼峰字段、实际发送的是下划线字段，三个必填项被发成 `undefined` |
| **卡在哪一步** | 第 3 步（学生填写页提交） |
| **他的原话** | 「我明明都填了，为什么还是不对」 |
| **归类** | ☑ **数据丢失**（本次新增类别，不在原预设五类里） |
| **为什么是最高优先级** | 主流程 100% 断裂，功能等于不可用；且用户看不到任何可行动线索，只能反复检查自己填没填 |
| **修复方案** | `submitStudent(row)` 改为直接透传契约格式，字段名映射只保留在 `toRow()` 一处 |
| **风险** | 低。改动只涉及数据序列化层，不动接口契约、不动数据库结构。已用完整字段 curl 验证服务端本身正常 |

### 关键教训（比这个 bug 本身更值钱）

1. **前端校验通过 ≠ 提交的数据是对的。** 校验查的 key 和发送的 key 可以是两套命名，
   本地开发、单元测试、curl 测接口全都测不出来 —— 只有真人真机点一次才会暴露。
2. **字段名转换只能在一个地方做**，且调用方与被调用方必须说同一种语言。
   `toRow()` 已转下划线、`submitStudent()` 又按驼峰取一遍 = 必然打架，且静默失败。
3. **只改表象不查根因等于没修。** 第一轮我把报错文案改友好、加了日期引导，
   部署后好友仍然提交失败 —— 因为我用手写完整字段 curl 成功就错误地断定「后端没问题」。
   curl 天然测不出浏览器序列化环节的 bug。
