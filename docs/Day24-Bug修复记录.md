# Day 24｜Bug 修复记录：添加房间按钮可连点提交

> 日期：2026-10-09
> 板块：① 复现 ② 定位 ③ 修复 ④ 验证留证

## 0. 一句话结论

**前端「添加房间」按钮没有 `disabled` 绑定**，快速连点会发出多个 POST。
后端 `unique(camp_id, room_no)` 挡住了重复数据，**但没挡住用户体验**——
用户看到的是「我明明点了一次，怎么弹了 4 次错」。

**后端和数据层是好的。问题只在前端一行代码。**

---

## 1. 复现

### 1.1 现象

在「+ 添加房间」表单里填好房号和容量，**快速连点「添加」按钮 5 次**：

- 数据库：新增 **1 间** 房（正确）
- 页面：**弹 4 次红色报错**，内容都是「房号 XXX 已存在(房间 id=…,容量 …),请换一个房号」
- 表单被清空并自动收起

### 1.2 复现步骤

1. 打开 `https://xinghe-helper-d5g92pis442fd9947-1499825718.tcloudbaseapp.com/workbench`
2. 点右侧「+ 添加房间」
3. 房号填 `RACE01`，容量填 `4`
4. **用鼠标快速连点「添加」按钮 5 次**（或聚焦在输入框里连按回车 5 次）

### 1.3 模拟并发请求（后端视角）

前端连点会同时发出 5 个 POST。用 curl 并发复现：

```bash
BASE="https://xinghe-helper-d5g92pis442fd9947.service.tcloudbase.com"
for i in 1 2 3 4 5; do
  curl -s -X POST "$BASE/api/rooms" -H "Content-Type: application/json" \
    -d '{"camp_id":1,"room_no":"RACE01","capacity":4}' \
    -o /dev/null -w "第$i 次: HTTP %{http_code}\n" &
done
wait
```

**实测输出**：

```
第1 次: HTTP 200
第2 次: HTTP 409
第3 次: HTTP 409
第4 次: HTTP 409
第5 次: HTTP 409
```

**查库确认**：

```sql
select id, room_no from public.rooms where room_no = 'RACE01';
```

→ **只有 1 行**（id=127）。

> **关键结论**：数据没坏。后端的唯一约束挡住了重复插入。

## 2. 定位：原因排序与排除

这是今天要掌握的方法——**不要看到一个现象就动手改，要先把可能性列全、再逐个排除**。

| # | 怀疑的原因 | 验证方法 | 结论 |
|---|---|---|---|
| 1 | **前端按钮没有 `disabled` 绑定** | 读 `Workbench.jsx` 的添加房间按钮 | ✅ **确认成立** |
| 2 | **前端函数没有连点判断** | 读 `handleAddRoom` 函数体 | ✅ **确认成立** |
| 3 | 后端没有并发防护 | 并发 5 个 POST 实测 | ❌ 排除 — unique 约束挡住，1 个 200 + 4 个 409 |
| 4 | 数据库缺唯一约束 | 读 `db/schema.sql` | ❌ 排除 — `unique (camp_id, room_no)` 一直在 |
| 5 | 校验层失效 | 传 6 类刁钻输入实测 | ❌ 排除 — 全部正确拒绝 |
| 6 | `await` 没写导致同步执行 | 读 `handleAddRoom` | ❌ 排除 — `await addRoom()` 在的 |

### 2.1 排除过程里最有价值的两步

**第 3 步（并发实测）决定了 Bug 的性质**：
如果没有这一步，很可能会跑去「加固后端」——但后端本来就是对的。
**如果数据真的被写坏了 5 间，那这就是另一个严重得多的 Bug。**

**第 5 步（刁钻输入）排除了校验层**：
这一步用的是清单里「卡住降级」给的手段。校验层全部正确，
说明问题不在「参数合法性」，而在「同一个合法参数被提交了 5 次」。

### 2.2 真正的根因

```jsx
// web/src/pages/Workbench.jsx 第 529 行（改前）
<button className="btn-primary room-add-btn" type="submit">
  添加
</button>
```

```jsx
// 同一个文件里，AI 分房按钮（第 397 行，改前）
<AsyncButton ... disabled={!!busy} />        ← 有防护
<button className="btn-plain" ... disabled={!!busy || aiStatus !== 'idle'}>
  重新分房                                  ← 有防护
</button>
```

**同一个文件里其他 3 个按钮都写了 `disabled={!!busy}`，唯独添加房间漏了。**

这不是「没考虑到」，是**漏了一处**——所以要找的其实是「同类写法在别处是什么」，
而不是「这个按钮应该怎么写」。

### 2.3 为什么 `busy` 状态是现成的

```js
// handleAddRoom 第 284 行（改前就有的代码）
setBusy('保存中…')
await addRoom(roomNo, cap)
...
setBusy('')
```

`busy` 状态**早就在设置和清空了**，只是没人拿它来禁用按钮。
状态有了、逻辑有了，**只差一个绑定**。

## 3. 修复

### 3.1 改动（`web/src/pages/Workbench.jsx`）

**第一处：按钮加 `disabled`（第 547 行）**

```jsx
// 改前
<button className="btn-primary room-add-btn" type="submit">
  添加
</button>

// 改后
<button className="btn-primary room-add-btn" type="submit" disabled={!!busy}>
  {busy || '添加'}
</button>
```

`{busy || '添加'}` 是把 `busy` 的文案显示出来——按钮变灰时用户能看到
「保存中…」，而不是以为按钮坏了。`busy` 的取值本来就是
「保存中… / 删除中… / 正在分房…」这类文案，直接复用。

**第二处：函数入口加判断（`handleAddRoom` 开头）**

```js
async function handleAddRoom(e) {
  e.preventDefault()
  if (busy) return          // ← 新增
  const roomNo = newRoom.room_no.trim()
  ...
}
```

**为什么按钮的 `disabled` 还不够**：

`<form>` 里按**回车键**会直接触发 `onSubmit`，这条路径完全不经过按钮，
`disabled` 拦不住。用户如果把光标放在房号输入框里连按回车，同样会重复提交。

所以是**两件套**：

| 防线 | 拦什么 |
|---|---|
| 按钮 `disabled={!!busy}` | 鼠标点击 |
| 函数入口 `if (busy) return` | 回车提交 / 程序化调用 |

### 3.2 为什么不用现成的 `AsyncButton` 组件

`AsyncButton`（`web/src/components/AsyncButton.jsx`）确实更完整
（自带转圈动画、`aria-busy`），但：

- 它需要页面维护一个独立状态（`status`），而 `busy` 已经是这个角色了
- 本文件第 397/401/404 行用的是 `disabled={!!busy}` 的写法，
  保持一致更重要 —— 同一个文件里两种写法会让后来的人困惑

**选改动最小、和现有代码一致的那个。**

## 5. 顺手发现但今天不修（按清单要求「记录下来」）

清单明确写了「今日不做：顺手修别的 Bug（记录下来）」，所以这两个**只记录、不动手**：

### 5.1 容量没有上限校验

**位置**：`cloudfunctions/api-rooms/index.js` 的 `validateCapacity()`

**现象**：后端接受 `capacity: 99999`（实测创建成功，id=125）。
只有前端 `<input max="10">` 挡着。

**风险**：如果有人绕过页面直接调接口，能建出一间「能住 99999 人」的房间。
不会造成数据损坏，但明显不合理。

**建议**：加一条上限校验，如 `capacity > 20` 报「可住人数最多 20」。

**优先级**：低（正常用户碰不到，前端已挡）。

### 5.2 `flash` 判断用英文匹配，可能永远不成立

**位置**：`web/src/pages/Workbench.jsx` 第 292 行（改前）

```js
flash(err.message.includes('duplicate') ? `房号 ${roomNo} 已经有了` : err.message)
```

**问题**：这行在判断错误信息里有没有英文单词 `duplicate`。
但 **Day 23 已经把服务端错误全改成中文了**，现在返回的是
`房号 301 已存在(房间 id=101,容量 4),请换一个房号` —— **不含 `duplicate`**。

所以这个三元判断永远走 `else` 分支，那句友好提示**从来没生效过**。

**建议**：改成判断错误码而不是文案：

```js
flash(err.code === 'ROOM_NO_DUPLICATED' ? `房号 ${roomNo} 已经有了` : err.message)
```

**优先级**：低（不影响功能，后端返回的中文提示已经够清楚）。

**但这条值得记**：它是 **Day 23 那次改动的遗留问题**——
改文案的时候没检查有没有别的地方在按旧文案做判断。
**改一处要记得看还有谁依赖它。**

## 6. 今天学到的

### 6.1 定位方法：列全可能性，逐个排除

不要看到一个现象就动手改。正确顺序是：

1. **把可能的原因列全**（我列了 6 个）
2. **给每个原因设计一个能证伪的验证方法**
3. **按「改动成本」从低到高验证**（先读代码，再实测，最后才想改架构）
4. **找到第一个能解释全部现象的原因，停手**

第 3 步尤其重要：**并发实测决定了这是「体验 Bug」还是「数据损坏 Bug」**，
两者的严重程度差着数量级。

### 6.2 「同类写法在别处是什么」是定位捷径

找 Bug 时，问「这个按钮应该怎么写」不如问「**同一个文件里其他按钮怎么写的**」。

`AsyncButton` 组件和 AI 分房按钮早就用了 `disabled={!!busy}` ——
漏的不是「不会写」，是「少写一处」。**照着邻居写，比自己想设计更可靠。**

### 6.3 修 Bug 要看「这条路径绕得过我吗」

按钮加 `disabled` 后，我发现回车提交能绕过它。
**修完问一句「还有别的路能进来吗」**，是这次多写一行 `if (busy) return` 的原因。
